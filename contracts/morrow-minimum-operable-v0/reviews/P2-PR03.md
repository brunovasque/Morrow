## Passe de Security Reviewer

| ataque/erro | defesa comprovada |
|---|---|
| target ausente, desconhecido ou desligado | `INVALID_REQUEST`, `TARGET_NOT_FOUND` ou `TARGET_DISABLED`; não existe fallback |
| papel com versão errada ou não permitido pelo target | recusa exata antes de skills/capabilities |
| skill autoescolhida pelo agente | precisa existir, estar habilitada e ser permitida por target, papel e pela própria skill |
| capability inexistente, desligada ou não autorizada | recusa por registry, target ou papel; requisitos de papel/skill também são obrigatórios |
| secret policy ausente | bloqueia mesmo quando o pedido não solicita material, evitando política implícita |
| segredo/finalidade/consumidor/capability divergente | regra precisa coincidir exatamente e usar capability `secret-use` já resolvida |
| comando, token ou campo escondido no request | objeto estrito rejeita qualquer campo extra antes da resolução |
| downgrade/ambiguidade de versão | referências são exatas e a seleção aceita no máximo uma versão por ID |
| configuração muda depois do gate | registries clonam e congelam profundamente os descritores; resultado também é congelado |
| prototype/accessor/Proxy hostil | objetos não simples e accessors são recusados; exceções de Proxy viram recusa sanitizada |
| aprovação de segredo fabricada por cópia | broker aceita somente o objeto emitido pelo resolver na mesma instância |
| emissor devolve token/value/material | handle tem quatro campos exatos; qualquer extra recusa o objeto inteiro |
| handle vai para outro consumidor ou dura demais | consumidor precisa coincidir e TTL máximo é cinco minutos |
| retry concorrente duplica emissão | uma aprovação compartilha uma operação idempotente; handle ID reutilizado entre aprovações é recusado |
| emissor vaza erro sensível | exceções e objetos hostis viram códigos sanitizados sem texto original |

## Achado bloqueante e resolução

Na primeira revisão remota, o Security Reviewer verificou que `SecretBrokerBoundary.issue()` aceitava o horário como argumento da própria chamada. Um chamador que já tivesse uma aprovação poderia fornecer um instante antigo e influenciar a validação de expiração do handle.

O hardening `73c353a` removeu o relógio da superfície de chamada. Agora o broker recebe uma fonte de tempo confiável na construção, usa essa fonte internamente e ignora qualquer tentativa do consumidor de escolher o instante de validação. A contraprova inclui handle expirado e TTL acima do limite sob relógio fixo controlado pelo kernel.

O head corrigido foi publicado e conferido pela referência Git e por `gh pr view`. Resultado: `BLOCKING -> RESOLVED`.
